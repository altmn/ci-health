# CI Health Optimize

Shorten the time from push to the requested useful decision, ready staging deployment or published release. Remove avoidable work and judge the result against meaningful detection, first-pass reliability and runner demand. Diagnosis, implemented changes and performance acceptance are separate outcomes.

1. Read repository instructions and [optimization guidance](../ci-health/references/optimization.md). Bind the exact source/candidate, required contracts, explicit target and start/finish evidence. Map PR, protected-push, reuse/fallback and downstream consumers relevant to that target. Staging, required verdict, release publication and production promotion have different endpoints. For a broad audit or baseline use [CI Health](../ci-health/SKILL.md); for a pre-push diff review use [CI Health Preflight](../ci-health-preflight/SKILL.md).
2. Trace the limiting commands through wrappers, fixtures, inner loops, setup, teardown and reporting using [execution guidance](../ci-health/references/execution.md). Identify the slowest valid dependency path separately from aggregate demand; account for actual project filters, worker capacity, repeated preparation and resource tails. Compare removing, reusing, moving and safely overlapping work before adding capacity or migrating tools. Choose the smallest effective remedy supported by evidence; source counts establish work, not timing. Gather the smallest useful observation when uncertainty would change the choice.
3. Before experiments or performance acceptance, read [experiments](../ci-health/references/experiments.md) and retain its scenario acceptance ledger across audit, preflight and shipping handoffs. Preserve the original targets and choose representative rows for the changed mechanism: full/selected PR, protected valid-full reuse, genuinely missing-proof fallback, invalid/stale/partial proof, relevant cold layers, failure diagnostics and the requested terminal milestone. A narrow change needs only relevant rows; unknown observations remain open.
4. Implement and verify within the caller's authorized scope. Advice/diagnosis stays read-only; requested fixes include appropriate validation. Qualify changed selection, artifacts and gates with [selection and reuse](../ci-health/references/selection-and-reuse.md), including actual failure/fallback consumers. Preserve mandatory evidence and exposure contracts; existing authority governs any protection change, push, deployment or cache mutation. Run preflight before the next authorized push and refresh affected inspection after edits. Keep first failures and unsuccessful alternatives in the ledger.
5. Follow the authorized validation through its actual endpoint. Compare compatible baseline/candidate conditions and all attempts/outcomes, including failed, cancelled, retried, no-publication and green-over-budget runs. Verify exact inventory and required checks, cold receipts for cold claims, actual publication for sealing, and remaining target margin. A fast reuse or PR arm does not qualify full cold protected fallback. Recompute the bottleneck after major changes and continue with the next supported remedy when required acceptance remains unmet, within scope.
6. Check the delivered plan against its calculations, actual edits and validation: shard members/totals, tables and prose must agree, with a missing/new timing policy. Report diagnosis, implementation and performance acceptance separately, with measured latency/demand, causal limits, unresolved rows, the exact next acceptance check and a concrete stop/rollback trigger. Close only observed accepted scenarios. Local success or a green workflow alone cannot establish the user's terminal budget. If implementation is done but required observations remain unavailable or pending, state that explicitly; do not report the overall improvement as successfully validated.
