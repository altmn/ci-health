# Bun in JavaScript and TypeScript CI

Use when a JavaScript or TypeScript repository already uses Bun or profiling identifies a toolchain step worth comparing. Pin and record the actual binary, runner image, runtime targets, lockfile and invoked scripts. Verify which command the pinned binary dispatches in the CI working directory. Evaluate tool replacement, concurrency and test selection independently where feasible. Use [execution.md](execution.md) for diagnosis and [experiments.md](experiments.md) for acceptance and rollout.

## Verify the pinned Bun version

| Feature | Version evidence and implications |
|---|---|
| `bun test --changed`, `--shard`, `--parallel`, `--isolate` | Shipped in 1.3.13. The 1.4 release documents fixes to per-file isolation. Verify flags and behavior on the installed version. [Bun 1.3.13](https://bun.com/blog/bun-v1.3.13) · [Bun 1.4](https://bun.com/blog/bun-v1.4) |
| `bun test --timings` and `--update-timings` | Shipped in 1.4.0. The 1.4.0 and 1.4.5 implementations split path-sorted files into contiguous, duration-weighted ranges. Workers use slowest-first dispatch and can steal work. [Implementation PR](https://github.com/oven-sh/bun/pull/36814) · [Tagged sharding source](https://github.com/oven-sh/bun/blob/bun-v1.4.5/src/runtime/cli/test/Timings.rs#L136-L189) |
| `bun check` | Shipped in 1.4.3. Bun reported 3–6.4× speedups over `tsc` 7.0.2 on selected projects. The reported 7.8× result compares Bun 1.4.4 with 1.4.3 on one project. Benchmark against the repository's actual checker, project mode and cache state. [Bun 1.4.3](https://bun.com/blog/bun-v1.4.3) · [Bun 1.4.4](https://bun.com/blog/release-notes/bun-v1.4.4) |
| `bun fmt` and `bun lint` | `bun fmt` shipped in 1.4.4. The built-in linter in tagged 1.4.5 source is canary-gated. On that stable version, `bun lint` may invoke the project's own script. Verify command availability and resolution before treating it as a replacement. [Formatter release](https://bun.com/blog/bun-v1.4.4) · [Tagged linter source](https://github.com/oven-sh/bun/blob/bun-v1.4.5/src/runtime/cli/lint_command.rs#L20-L24) |

## Qualify a tool replacement

Replay the current and candidate commands on the same revision and comparable runners. Use passing revisions and representative known failures. Keep the existing gate authoritative while comparing coverage, results and resource use.

| Replacement | Evidence to compare |
|---|---|
| Vitest or Jest → `bun test` | Discovered and executed tests by project, runtime, platform and feature configuration. Compare missing and extra cases, mocks and fake timers, setup/teardown, snapshots, DOM and browser environments, transforms, coverage thresholds and JUnit ingestion. Retain Node or browser execution where those environments are part of the contract. [Bun test runner](https://bun.com/docs/test) · [Node compatibility](https://bun.com/docs/runtime/nodejs-compat) |
| `tsc` → `bun check` | Project references, invocation mode, included files, intentionally failing diagnostics and exit behavior. Compare the existing TypeScript version and incremental mode. Keep separate declaration or build emission where consumers require it. Running `bun test --check` can cover a different project scope from a standalone check. [Bun type checking](https://bun.com/docs/runtime/check) |
| ESLint or Oxlint → another linter | File coverage and ignore rules, equivalent diagnostics by rule and severity, custom plugins, type-aware rules, warning thresholds and exit status. Keep the existing checker for rules the candidate cannot enforce. |
| Prettier or Oxfmt → `bun fmt --check` | File and language coverage, ignore rules, plugin behavior, format differences and exit status. Review intentional output changes separately from timing gains. [Bun formatter](https://bun.com/docs/format) |

Measure checkout, install, tool startup and useful work with representative cold and warm inputs. Include peak memory, queue and upload overhead when material. If repeated backend startup is costly, check whether each worker can safely reuse an immutable build while isolating ports, databases, temp directories and mutable state. Sharing a compatible artifact between machines requires exact input identity, trusted provenance and measured transfer cost. [Cache and result reuse](selection-and-reuse.md#cache-and-result-reuse)

## Pilot affected tests

1. Resolve and record the actual checked-out candidate SHA and contract-specific base. A PR head comparison can use its Git merge base when that matches the validation contract. A synthetic merge or merge-group candidate needs the appropriate base for the combined tree. On the default branch, account for changes since the last qualified revision where the policy requires it. Obtain enough Git history and start from a controlled checkout. `bun test --changed=<base-sha>` uses the supplied ref for its diff and can include untracked files. [Selector implementation PR](https://github.com/oven-sh/bun/pull/29262) · [Tagged diff implementation](https://github.com/oven-sh/bun/blob/bun-v1.4.5/src/runtime/cli/test/ChangedFilesFilter.rs#L439-L445)
2. Inspect the diff with change statuses and old and new paths. The tagged selector only follows edges it can resolve in the candidate's import graph, treats packages as external during the scan and excludes paths missing on disk. Add explicit owner/consumer rules for deletions and renames, aliased workspace packages, runtime-selected imports and plugins, files read at runtime, fixtures and snapshots, generated inputs, and test setup. Broaden validation for changed lockfiles, configuration or workflow and planner inputs unless a qualified policy bounds their effects. [Tagged graph implementation](https://github.com/oven-sh/bun/blob/bun-v1.4.5/src/runtime/cli/test/ChangedFilesFilter.rs#L144-L154)
3. Preserve mandatory checks separately and record discovery, selection, omitted scope and reasons. Bun can exit zero when it selects no files. Require a policy-supported reason for a no-op. For missing base/history, unexplained empty results or uncertain ownership, run an approved broader suite or leave the gate nonpassing. [Tagged empty-selection behavior](https://github.com/oven-sh/bun/blob/bun-v1.4.5/src/runtime/cli/test_command.rs#L2216-L2265)
4. Shadow the proposal against full execution of the same candidate, then run the subset on its own to expose order, isolation and setup differences. Replay realistic failing changes, including deletion, shared fixtures and runtime-loaded inputs. Apply the [selection qualification and rollout procedure](selection-and-reuse.md#shadow-evaluation-and-recall) before enforcing the new gate.

## Balance work without changing membership

Record timings from representative complete runs in compatible environments. Scope histories by test configuration, runner class, Bun version and isolation or worker mode where those affect durations. Preserve the timing digest, measured coverage, age and fallback policy. If an individual file has no weight, Bun uses a median estimate for partitioning. Record that weight as estimated. When timing inputs are missing or unusable, use a common approved count-balanced plan or regenerate a qualified profile. [Bun timing documentation](https://bun.com/docs/test/parallel)

Pass identical timing inputs and selection settings to every shard. With `--update-timings`, pass a fresh, shard-specific output as the first `--timings` path and the shared read-only snapshot as the next one. Publish the next timing snapshot only after reconciling expected reports and timing coverage. Retain independently qualified weights for files skipped by a selective run and record their age. A planned empty shard can be valid when the selected inventory is smaller than the shard count. A missing or unexpectedly empty report needs investigation. [Timing update implementation](https://github.com/oven-sh/bun/pull/36814) · [Shard membership checks](selection-and-reuse.md#inventory-and-shard-invariants)

Compare count-balanced and timing-weighted schedules at fixed shard count first. Then test shard count and `--parallel=N` separately. Include the slowest shard, start-time skew, repeated setup, report fan-in, occupied runner time and required-verdict latency. `--parallel` implies file isolation by default. Challenge isolation changes with shuffled order, standalone runs and shared-service contention. Keep measured limits for CPU, memory and external services. [Parallel and isolated test runs](https://bun.com/docs/test/parallel)

## Promote on evidence

Capture the baseline before switching any required mechanism. Keep the old path during qualification, pilot a bounded scope with explicit acceptance thresholds, and preserve a direct route to restore the previous runner, tooling or full suite. Required missing evidence, unsupported diagnostics, stale manifests and missed regressions warrant correction or rollback. If the candidate has only local replay evidence, report measured local effects and leave busy-hour queue and production gate impact unknown. [Experiment and rollout procedure](experiments.md)
